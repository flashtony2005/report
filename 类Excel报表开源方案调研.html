OpenPrint · 技术选型调研

类 Excel 非线性报表：GitHub 开源方案盘点

调研对象：润乾式「单元格扩展模型 / 主格树 / 层次坐标」报表引擎。数据取自 GitHub API 实时查询（2026-09-12），star 数与最近推送时间为当日实值。

结论：同类方案有一批，但全部在服务端；浏览器侧（JS/TS）没有任何开源实现。

  • 服务端开源有 6 个可用选择：积木报表、UReport2、NopReport、CellReport、SpringReport、Luck-Report。除 UReport2 已停更外，其余均活跃。
  • 前端只做"表格编辑器"：Univer / Luckysheet / FortuneSheet 都是网格 UI 组件，不含主格树、递归扩展、层次坐标——这些算法一个都没实现。
  • 对 OpenPrint 的含义：没有可搬运的 JS 引擎，新增 grid 模式仍需自研；但算法有现成参照，其中 NopReport 的核心仅约 3000 行，是最值得先读的源码。

一、按"有没有目标算法"分类

判断标准很关键：不能按"是否叫报表"分类，要按"是否实现单元格扩展"分类。很多高星项目名字里带 report，但走的是完全不同的技术路线（带状版式或模板填充），无法用来支撑类 Excel 报表。

三、为什么浏览器侧没有开源实现

「纯前端开源 · 单元格扩展引擎」：未找到

开源界对这套算法的实现无一例外落在服务端（Java / .NET），原因有三层：

  • 历史原因：该算法诞生于 Java 报表软件时代（润乾 → 帆软 → UReport2/CellReport），生态、文档、教程全在服务端；前端只被当作"渲染结果的容器"。
  • 工程惯例：这类引擎天然要吃 JDBC 数据集、连多个库、扛大数据量，服务端是更自然的落点；前端组件因此只需实现网格交互。
  • 算法难点被低估：真正难的不是网格，而是递归扩展 + 主格拉伸（合并）+ 层次坐标求值。开源前端库都停在"网格 + 公式"这一层，从未跨过去。

四、对 OpenPrint 的三条可行动建议

  1. 先读 NopReport 的 3000 行核心，再下手写 Apache-2.0 授权、代码极简、且它把层次坐标只做成"表达式解析器上的几十行扩展"——这与 OpenPrint 现有 layout-engine/expression.ts（896 行，已有 tokenize / parse / eval 骨架）的思路高度接近，移植成本最低。次级参考是 UReport2 的 ReportDefinition 与单元格父子格模型，最经典、可读性最好。
  2. 设计器 UI 不要自研网格，选 Univer 或 FortuneSheet 两者都是活跃的 TS/MIT-Apache 项目，可直接装进 React 工程。不要选 Luckysheet（已归档）与 x-spreadsheet（已迁移）。这能把工作量集中在扩展算法本身，而不是网格交互。
  3. 本地起一个对照基准，而不是只读源码 NopReport 与 UReport2 都能独立跑起来。先跑通"分组汇总"和"交叉表"两个样例，把输出结果当作自研引擎的验收基准；这样后面写 P1 算法原型时，正确性有客观参照，不必靠感觉判断。

本次调研确认的事实

  • 服务端开源选择充足，不必自研"完整平台"
  • 但 OpenPrint 是浏览器侧引擎，与服务端方案无法直接复用
  • 算法可参考；工程量仍在 OpenPrint 自己这一侧

与上一轮架构评估一致

  • 仍建议新增独立 document.type:'grid' + grid-engine，而非改造现有表格控件
  • 渲染 / 导出 / 打印 / 数据源可全部复用现有管线
  • 先做 P1 算法原型（主格树 + 递归扩展 + 层次坐标），跑通再定 UI
