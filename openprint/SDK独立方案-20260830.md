# 渲染引擎独立成 SDK —— 可行性评估与落地方案

评估时间：2026-08-30 · 结论：**可行，且能力基本已存在**

> **更新（同日已落地）**：评估通过后按「两者都要 + 一步到位」实施完毕。
> 双入口 SDK 已构建可用，首屏 2,137 kB → **176 kB**。详见 [八、落地结果](#八落地结果已完成)。

---

## 一、结论先行

| 问题 | 答案 |
|------|------|
| 设计器和渲染引擎是分开的吗 | **是**，且解耦做得干净（实测证实，见下） |
| 能独立成 SDK 吗 | **能**。打包已实测跑通，产物零 Vue |
| 需要重写吗 | **不需要**。`src/core/headless/` 已经是一个现成的编程式入口 |
| 主要障碍 | ① 体积 2.1 MB（可优化到 162 kB）② 从没配置过 lib 构建与 npm 发布 |

**最关键的发现**：你要的那个 SDK，代码早就写好了 —— `src/core/headless/createHeadless.ts`
提供 `render` / `exportPdf` / `exportJpg` / `exportSvg` / `print` / `buildRequest` / `dispose`，
文件头注释明确写着"零 UI、不挂载任何可见 DOM、可直接被使用者的脚本调用"。
**缺的只是"打包发布"这一步。**

## 二、引擎纯度实测

用 vite lib 模式对引擎层单独打包（POC，产物已清理）：

| 检查项 | 结果 |
|--------|------|
| 打包 | **成功**，283 modules |
| 产物 | `openprint-sdk.js` 2,137.43 kB / gzip 440.95 kB |
| 产物中 Vue 特征串 | **命中 0 次** —— 零框架依赖属实 |

**为什么能做到**：`src/core/` 唯一的 vue 污染源是 `fonts/system.ts`（用了 `ref`/`computed`），
而它只被 design 层 5 个文件引用（`usePrinterProbe` / `TextProps` / `RichTextEditor` / `CellToolbar` / `PreviewPanel`）。
引擎主链 `sdk → pagination-engine → renderer-html → measure` **完全不碰它**。

## 三、体积：唯一需要认真处理的问题

| 方案 | 未压缩 | gzip |
|------|--------|------|
| 完整 SDK | 2,137 kB | 441 kB |
| 只导出 `render` + `renderHtml` | 2,119 kB | 436 kB |
| 剔除重依赖（external 实测） | **162 kB** | **46 kB** |

**注意第二行**：只导出两个 API 也只少了 18 kB。说明体积与"导出多少 API"无关，
**重依赖是被静态 import 拖进来的**：

| 位置 | 静态引入 | 后果 |
|------|----------|------|
| `data-binder.ts:10` | `@bwip-js/generic`（条码） | 只要渲染就强制加载 |
| `data-binder.ts:12` | `qrcode` | 同上 |
| `mathkit/index.ts:11` | `katex`（公式） | 同上 |
| `mathkit/index.ts:18` | `katex/dist/katex.min.css` | 另产出 **CSS 1,459 kB** |

条码 + 二维码 + 公式合计 **1,975 kB（占 92%）**。

**结论**：瘦身路径只有一条 —— 这三个改成动态 import，按模板里是否真的用到该控件来按需加载。
改完核心可降到约 162 kB / gzip 46 kB，对"引入就能用"的 SDK 来说相当轻。

> 补充：`jspdf` / `opentype` / `html2canvas` / `svg2pdf` **已经是动态 import**（导出时才拉），
> 这部分没问题，不用动。

## 四、环境边界（实测）

用 `// @vitest-environment node` 在无 `document` / `window` 下实测：

```
typeof document = undefined
typeof window   = undefined
pages = 1 | html 长度 = 41052 | warnings = []
```

**纯 Node 下 render() 正常产出 41 KB HTML。** 原因是 `measure.ts` 是双模设计 ——
有 DOM 走真实排版，无 DOM 走 CJK 字符宽度估算兜底；`renderHtml` 是纯字符串拼接。

| 能力 | 浏览器 | Node 服务端 |
|------|--------|-------------|
| 排版 + HTML 渲染 | 可用 | **可用（实测通过）** |
| SVG 导出 | 可用 | 可用 |
| PDF / JPG 导出 | 可用 | **不可用**（`rasterize.ts` 需 canvas + DOM + foreignObject） |
| 静默打印 | 需装本地客户端 | 需装本地客户端 |

**所以 Node 端的正确用法是**：用 SDK 批量产出 HTML，再交给 puppeteer / wkhtmltopdf 转 PDF，
或者直接把 HTML 推给 Qt 打印客户端（默认 `http://127.0.0.1:18888`）。

## 六、两个需要你定的决策

**决策 1 · 目标形态**

- **A. 浏览器 SDK**（推荐先做）：React / Vue / Angular / 原生 JS 都能 `import` 后渲染 + 导出 PDF。工作量最小，能力最全。
- **B. Node 服务端 SDK**：批量出 HTML。PDF 得外挂 puppeteer。
- **C. 两者都要**：同一份代码出两个 entry（`index` 全量 + `node` 不含导出模块）。

**决策 2 · 是否先瘦身**

- 先发布 2.1 MB 版本跑通闭环，之后再动态化；
- 或直接做完动态化一起发（推荐，避免 API 二次变动）。

### 关键实现决策

**1. mathkit 拆成三份**（`core` / `index` / `async`）

设计器的 `MathViewLayer.vue` 在 `computed` 里同步调用 `renderMathControl`，没有 await 的机会；
引擎侧又必须动态加载。所以保留同步版给设计器、新增 async 版给引擎，两者共用 `core.ts` 保证结果一致。

**2. qrcode 的 CJS 互操作**

`@types/qrcode` 用的是 `export =`，TS 认为命名空间本身就是导出对象、没有 `.default`；
但运行时 ESM 下却挂在 `.default` 上。用 `(m as { default?: T }).default ?? m` 兜底，两种形态都能取到。

**3. 1.4 MB KaTeX CSS 的真相**

lib 打包时 Vite 会把 KaTeX 的 60 个字体 base64 内联进 CSS。`async.ts` 不 import
`katex/dist/katex.min.css`（只让同步版引），这一条就省下全部 1.4 MB。

**4. vue 列为 external 是防线不是优化**

引擎本就不依赖 Vue。万一有人误把 design 层的东西引进来，这里不会静默把框架塞进 SDK，
而是留下一个裸 import 让使用方立刻发现 —— 比悄悄膨胀 300 kB 好。
