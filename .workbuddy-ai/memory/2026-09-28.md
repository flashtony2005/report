## 首次 CI 真的跑了，而且是**红的** —— 顺带纠正我自己一个错误结论

用户让我「打开 Actions 页确认首次运行」。做的时候发现**我昨天的判断错了**：

> 昨天我写「Actions 是否真的会触发 —— 本机 `gh` 没登录，**验不了**」。
> **错。** 这个仓库是 **public**，所以下面两条**裸 curl 就能读**，不需要 token：
>
> - `GET /repos/flashtony2005/report/actions/runs` → 有没有触发、结论
> - `GET /repos/flashtony2005/report/check-runs/{id}/annotations` → 失败原因
>
> 真正读不到的只有 **job log 正文**（`/actions/jobs/{id}/logs` → 403
> 「Must have admin rights to Repository.」）。

**可迁移判据：把「我这条命令做不到」当成「这件事做不到」之前，
先问「是不是换一条路就能读」。** 我为这个错误多花了一整轮。

### 事实（实测）

| 项 | 值 |
| --- | --- |
| run | #1 `36307181284`，`event=push`，sha `704cc94`，**conclusion=failure** |
| 耗时 | 作业 234s（`跑闸` 一步 **169s**） |
| 成功的步骤 | checkout / 装 Node / 装 Rust / **两份 `npm ci` 都成功** / 缓存 |
| 失败的步骤 | **8. 跑闸** |
| annotations | 1 error + 1 warning + 1 notice |

**两份 `npm ci` 成功**这一点很重要：说明我昨天做的**可移植性修复是对的**
（本仓 `node_modules` 优先那套）。

## 根因：闸依赖了一个**从未入库**的文件

第二次 run（带上诊断通道）的 annotation 直接给出了答案：

```
闸「3/7 ts-test（前端纯函数单测）」失败，退出码 1
Tests  1 failed | 238 passed (239)
❯ grid-report.spec.ts:966:30
找不到存盘报表样本 ${name}。找过：…
```

`grid-report.spec.ts` 有一条用例要读**真实存盘报表**当样本，
`ts-test.sh:89` 负责把它拷进临时 harness：

```bash
cp "$ROOT/print-server/reports/sales-by-region.json" "$WORK/reports/"
```

而 `.gitignore:44` 写着 **`print-server/reports/`** —— **整个目录被忽略**，
`git ls-files` 里那个文件是 **0 个**。于是：

- **本机**：文件在磁盘上 → 闸绿（一直是绿的）；
- **干净检出（= CI）**：文件不存在 → `cp` 静默失败 → 用例抛错 → 闸红。

**这是「本机能跑 ≠ 干净检出能跑」**，而且只在别人的机器上显形 ——
靠跑本地闸**永远发现不了**。

顺带查清：那个文件**不只是测试夹具**，还是服务端的**内置样例**
（`--run-report sales-by-region` / UI 的「内置样例」入口）。
所以它没入库意味着**干净检出里连内置样例都没有** —— 比「CI 红」更严重。
（Rust 侧不吃这个文件：`sample_template_has_two_header_rows` 用的是代码里的
`sample_template()`，所以 `cargo test` 在 CI 上是过的。）

## 修复

1. **`.gitignore`**：`print-server/reports/` → `print-server/reports/*`
   + `!print-server/reports/sales-by-region.json`。
   ⚠️ **必须用 `*` 而不是忽略整个目录** —— git **不允许重新包含被排除目录里的文件**，
   写 `print-server/reports/` 会让 `!` 例外**静默失效**。
   入库前核过内容：只有 `/tmp/report-demo.db`，**无本机路径 / 连接信息 / 凭据**。
2. **`ts-test.sh`**：显式判样本存在，缺了**大声失败 + `exit 2`**（= 没跑成，不是失败）。
   原来 `cp` 静默失败 → 报错只列「找过这些路径」，**看不出根因是文件没被提交**。
3. **`check-all.sh` 诊断通道的两遍走**（见下）。
4. **新增「干净检出」检查**（`verify-ci-workflow.py::fresh_clone_checks()`）：
   扫描 `scripts/*.sh` 里所有 `$ROOT/<相对路径>` 字面量，
   凡是**存在但未入库**的文件就报红（跳过 `node_modules`/`target`/`dist` 等产物目录）。

## 我自己写的东西里踩的两个坑

1. **诊断通道自己制造了「看不见的失败」。** 第一版是「一个闸连头带尾发完再发下一个」，
   12 条额度被第一个红闸的输出吃光 → **后面红的闸一条都不出现**。
   比没有诊断更坏：它看着像「只有这一个闸红了」。
   → 改成**两遍走**：先把每个红闸的名字报全（一行一个），再拿剩余额度补输出尾部。
   （实测：两个注入的红闸，两行闸名都在最前面 —— 这是**本地 stdout 的发射顺序**；
   ⚠️ **API / 界面上的显示顺序是另一回事**，见本文末尾「新观察」。）
   附带记下 GitHub 的硬约束：**每步 annotation 有上限**（实测 failure 级 10 条），
   超出的**静默丢弃** —— 所以「先报名字」不是风格问题，是正确性要求。
2. **`::error::` 在 API 里的 `annotation_level` 是 `"failure"`，不是 `"error"`。**
   我的 `--remote` 按 `"error"` 过滤 → **明明有 12 条 annotation 却报「一条都没有」**，
   还反过来怪 `check-all.sh` 没写原因。**假阴性比没写更坏**（它会让人去修对的东西）。
   已修。

## 新增：`--remote` 诊断模式

`python3 scripts/verify-ci-workflow.py --remote` —— 一行拿到
「最近一次 CI 绿没绿 / 红在哪」，走公开 API，不需要 token。
以前是手搓 curl + 写临时 python 解析，现在是一条命令。
（`--repo` 可覆盖，默认从 `git remote get-url origin` 推，不写死仓库名。）

  `git add` 回来 → 恢复绿。
- `ts-test.sh` 缺样本守卫：移走文件 → `exit 2` + 明确提示；还原后逐字节一致。

## 修完之后：**CI 又红了一次，是另一条同类问题**（`c63bcc8` → run #3）

推送修复（`7001981`）后 run #3：**闸 3 绿了**（未入库样本那条已修），
改红在 **6/7 cargo test** —— 诊断通道这次直接给出了闸名与退出码：

```
闸「6/7 cargo test（print-server）」失败，退出码 101
    printers::cups_tests::list_printers_degrades_to_empty
    未配置队列不算错误: 执行 lpstat ["-a"] 失败: No such file or directory (os error 2)
```

### 根因：**测试是宿主相关的假绿**（同一个「本机绿、CI 红」大类）

`list_printers_degrades_to_empty` 断言 `list_printers()` 返回 **`Ok(空)`**，
但那**不是它的契约**：

| 宿主 | `lpstat` | 结果 |
| --- | --- | --- |
| 本机 macOS | **自带** | 命令跑得起来、没配队列 → `Ok(空)` → **绿** |
| CI runner（ubuntu-latest） | **不带 CUPS 客户端** | `Command::new("lpstat")` 报 `ENOENT` → `Err` → **红** |

**产品行为没错**：降级发生在 `list_printers_handler` 的 `unwrap_or_default()`，
接口仍是 200 + `{ok:true,count:0}` —— 本文件顶部注释**一直这么写**。
错的是**测试把「接口降级为空」读成了「`list_printers()` 返回 `Ok(空)`」**
（docstring 第 7/13 行写「两路都失败时返回空列表」，与第 63 行
「任何 FFI 失败返回 Err（调用方降级为空列表）」**表述不一致** → 测试照前者写了）。

### 修法（`4c58d8d`）

1. 测试改钉**真契约**，分两条：
   - ① `run_cups("__no_such_cups_tool__", …)` **必须 `Err`** ——
     **不依赖宿主，确定性**（这才是 CI 的真实情形）；
   - ② 降级结果**字段自洽**（不断言「一定为空」—— 那取决于本机有没有配打印机，
     是**环境**不是**契约**）。
2. docstring 把「接口降级」与「`list_printers()` 返 `Err`」**拆开写**，
   消除歧义来源。

**故障注入**：把 `run_cups` 的 spawn 错误吞掉（`Err(_) => return Ok(String::new())`）
→ 该用例**红**（退出码 101，`expect_err` 处 panic）；还原后逐字节一致。
本地 `cargo test`：**546 passed / 0 failed**。

### ⚠️ 新观察：annotation 的**显示顺序**不是发射顺序（机制未定）

实测两次（run #2 / run #3）：我**先发闸名、后发输出尾部**，但 API 读回来
**闸名总在最后一条**。所以：

- **功能上没问题** —— 脚本自己把总量卡在 ≤10（pass 1 最多 7 行闸名 + pass 2 补到 10），
  所以**永远不会被上限截断**，10 条全在；
- 但**「先看到闸名」这个可读性意图没达成**，闸名落在列表末尾。

**机制没查清**，两种假说都被数据否掉一半：不是简单的「新的在前」（那 warning 应该在最后，
实测它在**最前**），也不是按 message 字典序（run #2 的排序顺序对不上）。
→ **没有把握就不改**：按猜的模型去「修」可能改得更坏。
记为**未决观察**，下次真要动它，先做一次「故意发 15 条、看哪 10 条活下来」的实验。

## 结局：**CI 绿了**（run #4 `4c58d8d4`）

```
#1  704cc945  failure  238s   ← 闸依赖未入库文件
#2  3fa9258f  failure  193s   ← 同一条，但诊断通道给出了闸名与原因
#3  7001981f  failure  182s   ← 换成 CUPS 测试（宿主相关假绿）
#4  4c58d8d4  success  267s   ← 17 个步骤全绿，annotation 只剩 2 条（都是无害的弃用/迁移提示）
```

本地全量闸同批：`通过 7 · 失败 0 · 没跑成 0` / `全绿` / `EXIT=0`。

### 这一轮的**真正教训**（比修好 CI 更值钱）

**两个根因是同一个病，换了两个器官：**

| # | 形态 | 本机为什么绿 |
| --- | --- | --- |
| 1 | 闸引用了**未入库**的文件 | 文件在磁盘上（从没被 `git add`） |
| 2 | 测试**依赖宿主有某个可执行文件** | macOS 自带 `lpstat`，Linux runner 不带 |

两者都是**「本机绿 ≠ 别人机器绿」**，而且**差别只在别人的机器上显形** ——
所以**靠跑本地闸永远发现不了**，只能靠
①一条专门盯它的检查（`fresh_clone_checks()`），或
②真的去读远端 CI 的结果（`--remote`）。

**推论：本地全绿不能作为「CI 会绿」的证据。** 我这两次都是
「本地 7/7 全绿 + 推送 + CI 红」，一次不多一次不少。
以后**推完必须去读 CI**，别把本地绿当成交付完成。

### 顺带确认的一件事

**诊断通道自己证明了它的价值**：run #2 / #3 的 annotation 直接给出
「哪个闸 + 退出码 + 闸自己的输出」，**我不需要 admin、也没看 job log** 就定位了两处根因。
如果没有它，这两轮我只能看到 `Process completed with exit code 1`。

## 第 3 档：把闸门搬回它该在的地方（同日，`改进`）

《架构体检》里唯一还没动的一档，5 条全做完。**但过程中挖出一个比这 5 条都大的缺口。**

### ⚠️ 真缺口：**676 条用例一条闸都不跑**

| 闸 | 实际覆盖 |
| --- | --- |
| 闸 3 `ts-test.sh` | `openprint/src/report/` —— **3 个** spec |
| 闸 7 `ts-test-designer.sh` | 显式 `--exclude '../openprint/src/**'`，只跑 `grid-report-*` |

而闸 7 那句排除的**理由**写着「那批由 ts-test.sh 用纯 node 环境跑」——
**那句是错的**：`ts-test.sh` 只覆盖 `report/` 一个子目录。于是：

> **openprint 的 70 个 spec 里 67 个（约 676 条用例）没有任何闸在跑，
> 而 `check-all.sh` 照样全绿。**

招牌形态「**闸是绿的、但没有跑器**」的又一次复发 —— 而且**有一句错注释替它打掩护**。
**错注释比没有注释更坏**：读到就放心了，没人会去核。

顺带纠正我自己的判断：我此前把「openprint 配了 `vitest.config.ts` 但没有 `test` 脚本」
记为「**CI 不修这个**（没接不算失败）」。**偏了** —— 它不是「没接」，
是**整个引擎层没有跑器**。

### 做了什么

1. **`openprint/package.json`** 加 `"test": "vitest run"` + `"test:record"`。
2. **新增闸 8** `scripts/ts-test-openprint.sh`（openprint 自己的 vitest，
   70 文件 / 915 用例 / ~240s）。**只加脚本不加闸 = 又造一个「没有跑器的闸」**，所以必须接。
3. **录制器不再静默重录 golden**（计划外但**必要**）：原来 golden 缺失就
   `writeFileSync` 然后 `return`（**通过**）—— 接闸之后这就成了「测试往仓库写文件」，
   且契约从「冻结在 `8ced46b`」静默退化成「当前代码自证」，退出码还是 0。
   改成默认只校验、缺失即失败；只有 `DESIGNER_CONTRACT_RECORD=1` 才录。
4. **修 `designer-react/.../designer-contract.spec.ts:27`** 的走不通提示语
   → 冻结事实 + 两条出路（从 git 取回 / 显式重录）+ cwd 警告。
5. **`ts-test.sh` 删掉两条 `/Users/...` 硬编码候选**（本仓两条都装着 vitest，
   那两条只是冗余；留着就会静默挑一个别人机器上不存在的目录）。
6. **`openprint/README.md` 新增「测试与覆盖边界」**（四条入口对照表 + 边界 + golden 冻结说明）。

### 第 2 条的原结论被**推翻**了（好事）

原计划是「给 4 个永久不跑的 spec 一个归宿：删掉或归档」。
实测：它们只是**没有跑器**，不是「没人要」。闸 8 一上，
2 个真孤儿（`dataSource` / `designer-duplicate`）立刻被跑到且**全绿**（13 用例）。
→ **不用删、不用归档。**

### 故障注入（录制器，四条全做）

① 基线通过且逐字节未改 · ② **移走 golden 不设开关 → 失败（退出码 1）且未重录**（核心）
· ③ 移走 + `DESIGNER_CONTRACT_RECORD=1` → 通过并录制 · ④ 还原后 sha256 一致。

### 代价与取舍

`check-all.sh` 全量 ~3.5min → **~7.5min**；CI job ~270s → ~510s。
换 676 条用例第一次有闸。符合本项目的排序：**「没有跑器的闸」比「慢的闸」坏得多**。
闸数 7 → 8，`check-all.sh` / `ci.yml` 的编号与 job 名一并改了，
顺手删掉 `ci.yml` 里那个会漂的「7 道闸」数字。
