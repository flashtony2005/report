## 图表格进服务端报表（差距分析 B1，做完）

背景：`引擎差距分析-对照积木报表.md` 的 B 类第一项 —— 画布有自研 `chartkit`
（bar/line/pie，纯函数出 SVG），服务端非线性报表**一格图表都没有**。

### 关键前提（没有它这事不成立）

`GridCell.pos` 保留**模板坐标** → 一个模板坐标能反查出它展开后的输出范围。
纵向（`A3` → 3 行）与横向（`B2` → 3 列）都能解析，因为按 `(行, 列)` 排序
出来就是阅读顺序。

### 设计决策（都不是随手定的）

1. **xlsx 用原生图表，不栅格化**。读了 `rust_xlsxwriter 0.99.0` 的源码确认
   `chart` 模块可用。栅格化成 PNG 会让图变**死图**（不可编辑、不可换类型、
   放大糊）。
2. **数写进表格下方的隐藏列**。展开后一个模板坐标可能落在**不连续**的行
   （嵌套分组时 `A3` 在 0/3/6 行），而 Excel 原生序列**只能引用连续区域**。
   代价照实说：**图表是导出那一刻的快照**，在 Excel 里改表格数字不会重算图表。
3. **空值是空档不是 0**。`Vec<Option<f64>>`：柱跳过 / 线断成多段 /
   饼不计入总量。「空着」和「就是 0」在图上看着一样，在报表里是两回事。
4. **一个声明只画一份**。图表格所在行会随别的格子展开 → 同一 `pos` 出现 N 次。
   图片**相反**（`from: value` 那种一列产品图，就该一行一张）。

### 交付物

- `chart.rs`：纯函数解析器（模板坐标 → 数据）。15 条单测。
- `chart_svg.rs`：服务端内联 SVG，镜像 `chartkit` 的布局常量。11 条单测。
- `xlsx.rs::write_charts`：原生 `Chart` + 隐藏数据块。
- `engine.rs::resolve_charts`：**整个网格填完之后**才解析（它读别的格子）。
- `mod.rs::to_html`：图片 > 图表 > 文本 三路优先。
- 类型两侧镜像：`CellChart` / `CellChartSeries` / `ResolvedChart` /
  `ResolvedChartSeries`，`mirror-check.py` 20 组全过。

### 三个「差点漏掉」的

1. **`cargo build` 干净 ≠ `cargo test --no-run` 干净**：加 `chart` 字段时
   build 报 17 处、test 又报 58 处（测试代码里的结构体字面量 build 看不见）。
   老教训再次生效。
2. **单测守不住「复制成 N 份」**：老断言只看第 0 行，全绿；拆包探针一眼看出
   3 个 `chartN.xml`。**探针的价值就在这类地方** —— 补了一条单测钉住「只画一份」。
3. **探针自己出过假红**：`cell_texts` 的正则不认自闭合 `<c r="C3" s="2"/>`，
   把它当开标签一路吞到下一个 `</c>`，于是 `G5` 的「销售额」被记成 `C3` 的
   → 报「表头读不到」。**修的是探针，不是产品。**

## 客户端 `chartkit` 的注释是错的（已更正）

`core.ts::niceMax` 的注释写「max=73 → 80；max=250 → 300」，但实现是
「取 1/2/5×10ⁿ 里第一个 ≥ max 的量级」→ 实际 **73 → 100、250 → 500**。
注释描述的是另一种算法（先算步长再乘刻度数）。

处理：**服务端跟实现对齐**（已写进单测钉住 100/500），并把 `core.ts` 的注释
改成实情 + 交叉引用。没改实现 —— 那会改掉所有现存图表的坐标轴刻度，
是行为变更不是 bug 修复。**若想改成 80/300，是一次独立的产品决策。**

## 环境事故：cargo registry cache 被清空

`~/.cargo/registry/cache/*.crate` 全没了（`src/` 解压源码还在），于是
`cargo build --offline` 报 `failed to download <pkg>`（cargo **不回退到
已解压的 src**），联网又卡在 `transfer too slow: failed to transfer more than
10 bytes in 30s`。

**误判过一次**：以为 `ahash` 是 dev-only 依赖，其实它经
`hashlink ← hashbrown 0.14` 进正常构建图。

**关键发现：慢的不是网络，是 cargo 的下载器。** 同一条 URL 用 `curl`
**4.7 秒**下完；cargo 自己 15 分钟只下完 40 个包。做法：从 `Cargo.lock`
列出缺的包，`curl` 直接落到 cache 目录。**并发最多 2** —— `xargs -P 8` 会
大面积触发 TLS `unexpected eof while reading`（沙箱代理限流）。补完后
`cargo build --offline` 秒过（有 sccache，编译只要 4~8 秒）。

顺带把 `fault-inject-chart-probe.py` 的 `build()` 改成**先试 `--offline`**，
别让驱动因为网络问题假装「注入没抓到」。
