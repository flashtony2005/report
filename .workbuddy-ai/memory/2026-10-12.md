### 🔴 工作树守卫一改就翻车，meta-check 的 D 案例抓到「守卫自己曾经是死的」

`INJECT_SCOPE` 自带 `^` + `tree_fp` 又拼 `^.. ` ⇒ 正则 `^.. ^(designer…)/src/`
**永远 0 匹配** = 守卫 inert。D（脏文件落 src/ 应 rc=2）当场红才暴露；去掉 `^` 后 D 绿。
**同时说明 E 此前是假绿**（它验「src/ 外不拦」，而守卫什么都没匹配，当然不拦）。
⇒ 这是「闸是绿的、但没有跑器」往上爬一层：危险的不是守卫错了，
是它**看起来在工作**（不拦 = 一切照常）而实际什么都没判。三个假脚本都要补进 CI_ABLE。

### 🔴 红因：**第四处本机写死路径**，而且它跨了一层进程

`docx-order-table.py` 里 `VENV = /Users/lushaohui/…/envs/default`，
`find_docx_package()` 拿它 `sys.path.insert` 找 `python-docx`。
CI 上那个目录不存在、oracle venv 里也没装 python-docx ⇒ 探针报「缺包」
（真相是「路径写错」）⇒ 基线红 ⇒ 注入不成立 ⇒ 退出码 2。

**链条**：`verify-docx.py` → `sys.executable` 起子进程 → `docx-order-table.py`
⇒「哪个 python 跑探针」==「用哪份 python-docx」。中间任一层写死路径就在那点断，
**而断点上的报错指向症状那一层，不是原因那一层。**

修法（比 `PY_BIN` 更彻底，不依赖任何路径）：`DOCX_ORDER_PKG` 显式覆盖 →
`import docx` 从当前解释器取包 → 都没有就退出并打印
`{sys.executable} -m pip install --only-binary=:all: python-docx`。
配套 CI oracle venv 加装 `python-docx`（**同一个 venv**，经 `PY_BIN` 传）。
扫尾：`verify-barcode.py` 的安装提示 `VENV_PY` → `sys.executable`；
`ts-check.sh`/`node-bin.sh`/`ts-project-check.sh` 的几条是候选回落，
`print-server/scripts/*-e2e.py` 手动跑 —— 都不是 CI 路径。

本机复验：`CI=true PY_BIN=<venv> --only docx` → **14/14 + 基线绿（171s）**。
全量 7 脚本复跑中（~933s）。
