## 每行带坐标的聚合：一个真 O(n²)（不是优化空间，是量级错误）

起因是文档里一句「仍未做：表达式缓存与增量重算（`resolve` 每次重新收集后代）」。
按项目惯例**先量后改**，结果比记录严重得多。

### 基准漏了这个形状

已有 9 个基准把「每行聚合」量得很细，但**全都不带层次坐标**：
`bench_per_row_agg` 量 `SUM(B2)`/`ACCSUM(B2)`，`bench_sibling_ref` 量 `B2 * 2`/`B2.sum()`。
不带坐标时 `resolve` 走 `pos_index` 的 `Rc` 克隆，本来就 O(1)。
而明细行最常用的 `C1[A1:+0].sum()`（**带**坐标）没有基准正面覆盖 ——
只在 `bench_excel_formula` 的「无公式」对照列里露了马脚（那个基准是给 excel 写的，
平方藏在对照列里，名字上看不出来）。

新增 `bench_per_row_agg_coord`（对照版把 D1 换成普通字段，相减即净成本）：

| 明细行数 | 本组合计 | 每行 |
| ---- | ---- | ---- |
| 500 | 2.8 ms | 5.6 µs |
| 2000 | 38.3 ms | 19.2 µs |
| 8000 | 560.8 ms | 70.1 µs |

每行成本随规模翻倍 → O(n²)。

### 一行上是**四处**叠加

第一版只给 `resolve` 的结果集加缓存：560 → 448 ms，**曲线几乎没动**。
（skill 里那句「只修了最显眼的那一处，剩下的几处仍在 O(n²)」原样重现。）
把这一行每一趟 O(n) 列出来才看清四层：

1. `resolve(target, coord, cur)`：每行重跑 `resolve_raw` + hidden 过滤 + `Rc` 分配
2. `aggregate_cells`：每行逐格 `JsonValue` 克隆再转 f64
3. `ensure_deps`：带坐标的表达式 `expr_is_cur_independent` 判 false →
   每行重新枚举依赖集（`out.extend(resolve(..))` 把整个集合复制进 Vec）
4. `ACCSUM` 的 `cells.iter().position(..)`：集合已升序却用线性扫

四层各接一次缓存后，8000 行：560.8 / 554.8 / 361.4 ms → **2.9 / 5.0 / 4.6 ms**。

### 缓存键：逐行的维度要做成**下标**，不是塞进键

`ACCSUM` 改了两版才对，两个方向都错过：

* 只放坐标 anchor → 键相同了，但 N 行共用第 1 行的部分和（第 2 行应 3 实际 1）→ **错值**
* 两个 anchor 都放进键（坐标 anchor + target 可见实例）→ 值对了，但键逐行不同 →
  **永不命中**，8000 行 149 ms，还是平方

正解：缓存集合的**前缀和** `prefix[i] = 前 i 个之和`，`ACCSUM = prefix[upto]`，
`upto` 由本行可见实例二分定位。键只留决定集合的 `(target, coord, 坐标anchor)`。
→ 教训：**先问「这个量为什么逐行不同」**；如果是「同一个集合取不同的前 k 项」，
那就是下标问题，不是键问题。

### 安全性依据（一句话，但要能验证）

`hidden` 只在 `compute_tests` 里变，而那是在 `evaluate_to_fixpoint` 每轮的**末尾**；
所有缓存在每轮开头跟 `pos_index` / `deps_done` 一起清空 →
「清空 → 求值整轮 → 改 hidden」之间集合与值都冻结。
`Filter` / `Var` 的依赖集不由 anchor 决定，`dep_key` 直接返回 `None`（保守不缓存）。

### 探针

* **故意改错**：`agg_of_numbers` 的 sum `+1` → 红；`ACCSUM` 的 `p+1` 改 `p` → 红
  （信息指到具体行：`ACCSUM(C1[A1:+0])：第 1 行应是 1，实际 0`）
* **强制退回旧路径**（5 个快路径全关）→ **161 条全绿** ← 语义保持的证据
* **数值钉死**：`per_row_coord_agg_values_are_exact` 用 1..=N 把三个口径写成闭式
  （SUM 每行=整组合计 / ACCSUM 第 k 行=1..k / PROPORTION=k/总计）。
  后两个逐行不同 → 「跨行串缓存」立刻暴露。上面那个键放错的 bug 就是它抓的。
  → **这类 bug 的特征是「输出仍是一串看着很正常的数，只是整体错位」**，肉眼读输出发现不了。

测试 160 → **161**；mirror 一致。

### 修法

* `Numbers` 补 `product`（PRODUCT）/ `non_null`（COUNTA，**与 `count` 不同**：
  count 只数能转数字的，non_null 连文本格也算）→ 整族共用**一份**缓存，
  不是每函数单开（键 + 失效点都要各自维护，迟早走偏）。
* `coord_nums_cache` 值由 `Numbers` 改 `Rc<Numbers>`：RANK 要拿 `sorted` 二分，
  按值取会克隆整个有序数组 → 每行 O(n) 克隆 = 等于没缓存。

改报**绝对耗时** + 最右一列基线 → 形状可直接读。

* 在 `cached_coord_numbers` 开头 `return None` 关掉整条快路径 → **162 条全绿**
  ← 语义保持证据。

## 又一层：给「没覆盖过的形状」补基准，量出一个**语义 bug**（已修）

接着同族审计往下查，发现 `{}` 格集过滤**从没有任何基准覆盖**（只有解析器测试 +
一条 `$` 语义测试）。补了 `bench_per_row_filter`，一量就是 O(n²)（2000 行 570ms）。
但追这个平方时发现真正的毛病是**条件被静默丢掉**：

| 表达式（数据 1..6、单组） | 应该 | 修前实际 |
| ---- | ---- | ---- |
| `C1[A1:+0]{$B1 == B1}` | 1,2,3,4,5,6 | 1,2,3,4,5,6 ✅ |
| `C1[A1:+0]{$B1 == B1}.sum()` | 1,2,3,4,5,6 | **21×6** ❌ |
| `C1[A1:+0]{$B1 == B1}.count()` | 1×6 | **6×6** ❌ |

* **根因**：解析器把聚合后缀挂在**内层** `Expr::Cell` 上（`expr.rs` 解析测试就是这么断言的），
  于是 `eval_ast` 先求内层 Cell（带聚合）→ 拿到**未过滤**的整组聚合并返回 `Val::Num`，
  `Filter` 分支随即 `other => return other`，条件整个没执行。
  输出仍是「一个看着很正常的合计」→ 静默错值。
* **修法**：`Filter` 分支里若内层 Cell 带 `Prop::Aggregate(f)`，摘下后缀 →
  先 resolve 格集、按条件筛、再对筛完的走 `agg_of_numbers`（复用整族口径）。
* **探针**：把提前 `return` 改成 `let _probe = …`（=退回旧路径）→
  `filter_then_aggregate_applies_the_condition` 红：`第 1 行应是 1，实际 21`。
* **测试**：`filter_then_aggregate_applies_the_condition`（5 个闭式口径 + 一条
  「带条件的和 ≠ 整组合计」防空转断言）。

### 性能：两处独立的平方，按现状记录不修

`bench_per_row_filter`（阶梯只到 2000，因为平方很贵）：三列带 `$` 的都 ~570ms@2000。
判别实验 `{1 == 1}` 常量条件（只承担依赖枚举）= 63ms@2000 → 说明是**两处**：
① `ensure_deps` 对 `Filter` 每行重枚举依赖（`collect_deps` 把整个结果集复制进 Vec）
② 逐候选求条件（N 格 × 两次 resolve + 主格定位 + `JsonValue` 克隆 + 转字符串，② 占 8/9）

**不修的理由**：`{}` 是「月份不连续」这类小分组场景的工具（组内十几行成本可忽略），
要修得给比较键建哈希索引。基准留在仓库当基线，判别列写进注释防被删。

### 教训（已写进 perf-quadratic-hunt skill）

1. **两个特性各自能跑 ≠ 组合能跑**：`{cond}` 单独对、`.sum()` 单独对，组合才丢东西。
2. **「某个形状慢」也可能是「它根本不该走这条代码」**：只看耗时容易去优化一段
   本该被短路的循环。**先确认结果对，再谈快慢。**

测试 162 → **163**；12 个基准无回归；TS 121/121。

## 再一层：过滤 × **每个**聚合函数的组合矩阵 → 又抓到一处静默变空

修完「条件被丢掉」之后没收手，把 `{}` 过滤 × 全部聚合函数排成一张表
（一条测试 15 种写法）一次跑完 —— 又抓到一个：

`ACCSUM(C1[A1:+0]{cond})`：`args[0]` 是 `Expr::Filter` 而非 `Expr::Cell`，
`ACCSUM` 的两条 `Expr::Cell` 分支都接不到 → 落到 `_ => Val::Null`
→ **出表是一格空白**，不报错、不告警。其余 14 种都对。

* **不实现**（累计要「当前实例在集合里的位置」，过滤后的集合不一定含当前实例，
  基准无从确定 —— 不臆造语义），但**让它说出来**：
  新增 `Engine.unsupported: RefCell<BTreeSet<String>>`（`eval_call` 是 `&self`，
  按 `var_misses` 老套路收集、`expand_sheet` 末尾统一转 warnings，并随其它状态一起清）。
* **探针**：把告警那段改成 `if false { … }`（=退回静默）→
  `filter_combined_with_every_aggregate` 红：`静默变空不行，必须给出告警。实际告警：[]`。
* **测试**：`filter_combined_with_every_aggregate`（15 种写法 + ACCSUM 的
  「空值且必须带告警」断言）。

### 教训（已写进 skill）

**修完一个组合，把组合矩阵整张过一遍**：bug 的形状是「特性 A × 特性 B 的某组合静默失效」，
正解是 A 的每种 × B 的每种排成表一次跑完，而不是只补刚发现那一格。
N 种写法 × M 种入口 = N×M 个组合；只测对角线永远发现不了组合问题。

**没实现 ≠ 可以不说**：「算不出来」和「没有数据」在报表上都是**一格空白**，
必须用告警区分开。

测试 163 → **164**；12 个基准无回归；TS 121/121；mirror 一致。

## 补一刀：`.expandIndex` 那一支也被漏掉了（已修）

上面那个修法只特判了 `Prop::Aggregate`。而 `Prop` 还有另一个变体 `ExpandIndex`，
`{cond}.expandIndex` 走同一条 `other => return other` → 条件同样被静默忽略。
实测三者结果**完全相同**（条件毫无作用）：

| 写法 | 结果 |
| ---- | ---- |
| `C1[A1:+0].expandIndex`（对照，无过滤） | 0,0,0,0 |
| `C1[A1:+0]{$B1 == B1}.expandIndex` | 0,0,0,0 |
| `C1[A1:+0]{$B1 != B1}.expandIndex` | 0,0,0,0 |

* **教训**：**特判枚举的一个变体时，先把枚举的所有变体列出来**。
  `Prop` 只有两个变体，当时却只写了匹配上的那一个。
* **改法**：对 `prop` 做**穷尽 match** —— `Aggregate` 先筛再聚合；
  `ExpandIndex` 按「不臆造语义、但必须说出来」→ 告警 + 空值
  （expandIndex 是「本格在主格下的序号」，筛完的集合未必含本格，序号无定义）。
* **探针**：`if false` 包住告警 → 红：
  `C1[A1:+0]{$B1 == B1}.expandIndex：静默忽略条件不行，必须给出告警。实际告警：[]`

## `{}` 过滤的「O(n²)」：量了之后决定**不做**

清单里排第一的待办（修 `Filter` 的 O(n²)）**被测量推翻了**。原基准 `bench_per_row_filter`
用的 `one_group_data` 把 N 行全塞进**一个组**，量的是「一个巨大的组」这个极端形状；
而 `{}` 的真实用途是「月份不连续」这类**小分组**。

新增判别基准 `bench_filter_group_size`（**固定总行数 2000**，只改每组行数 g）：

| g | 组数 | 带 `$` | 不带 `$` | 基线 |
| --- | --- | --- | --- | --- |
| 10 | 200 | 19.4 ms | 11.1 ms | 2.7 ms |
| 20 | 100 | 21.6 ms | 11.9 ms | 2.4 ms |
| 80 | 25 | 38.4 ms | 18.3 ms | 2.2 ms |
| 200 | 10 | 71.7 ms | 30.4 ms | 2.3 ms |
| 2000 | 1 | 581.3 ms | 223.2 ms | 2.3 ms |

**结论：成本是 O(总行数 × 组大小)，不是 O(总行数²)。** 同样 2000 行，每组 10 行
只要 19 ms。所以原记录「小分组下可忽略、不建投机性索引」是对的 —— 现在有数据支撑。

* **教训（给自己的）**：光看「2000 行 570 ms、翻倍变四倍」就把它排成第一优先，
  是**只看曲线不看数据形状**。基准的数据形状本身就是结论的一部分，
  换形状可能差 30 倍（581 → 19）。
* 已在 `bench_per_row_filter` 的注释里加了 ⚠️ 警告，避免下次又被自己误导。
* 触发条件记清楚了：只有「单组几千行」才痛；真要修是给比较键建哈希索引，
  且**只对 `$X == Y` 等式形状可索引**，一般条件索引不了。
* 未改引擎代码，只加基准 + 注释 + 文档。测试 165 全绿、13 个基准（新增 1 个）、零告警。

## 预览区分页：后端一直在给，前端一直没读

清单第 2 条（「预览区始终展示未分页的完整表」）。根因很清楚：
**`RenderResponse.pages` / `pages_html` 后端一直在返回，而 `GridReportModal.tsx`
里一次都没提过 `pages`** —— 只读 `data.sheets[0]`。于是开了「分页 + 每页 20 行」，
预览仍是完整表，要验分页只能导出 xlsx。

### 改法
* 取页逻辑抽成**纯函数** `pickPreviewSheet(data, pageIndex)`，放进共享镜像
  `openprint/src/report/grid-report.ts`（designer-react 经 alias `@/*` → `openprint/src/*` 复用）。
  规则：`pages` 非空取当前页；否则回落 `sheets[0]`；**越界夹到最后一页**
  （重新渲染后页数变少，而 `pageIndex` 还停在旧值上）。
* 弹窗加「上一页 / 下一页」+ `i / n` 指示器（`pages` 非空**且非自由模板模式**才显示）。
* **切页不重新请求**：服务端一次就把所有页都回了，只是以前没人用它。
  用 `lastRenderRef` 存最近结果，`paintSheet(idx)` 只重画画布；
  `paintedIndexRef` 防止「重渲染」与「切页」两个 effect 重复重画。

### 踩到的坑（值得记）
1. **TDZ**：`runReport` 的 `useCallback` 依赖数组里引用了 `paintSheet`，而 `paintSheet`
   声明在它**后面** → `TS2448/TS2454 used before its declaration`。
   **依赖数组是渲染期求值的**，不是回调体内 —— 所以块级声明必须挪到前面。
2. **先量基线再改**：tsc 本来就有 **3 条既存错误**（`DbEngine` 类型、`"border"` 比较）。
   先 `git stash` 量出基线 3，改完再比 → 确认自己**新增 0 条**。
   不量基线就会把既存错误算到自己头上（或反过来放过自己新加的）。

### 验证
* tsc：改完仍是 **3 条**（= 基线），新增 0。
* 前端单测 **121 → 125**（新增 4 条）；`mirror-check.py`：镜像一致。
* 探针：把 `pickPreviewSheet` 换回「永远取完整表」→ **3 条红**
  （`expected '完整表' to be '表 (1/3)'`）；回落完整表那条**正确地保持绿**。
  还原后与备份 diff 一致。

### 顺带查清一个**既存的 flaky 测试**（不是本次引入的）
`designer-react` 全量 `npm test`（96 文件 / 999 用例）里，
`TopToolbar.spec.tsx > 渲染品牌 / 模板名输入框 / 主操作按钮` 会 **20 s 超时**。

* 单独跑这个文件：**15/15 通过**，而这一条要 **4796 ms**（同文件其余用例只 ~0.6 s）——
  它是文件里的**第一条**，把模块初始化 + 首渲染的成本全吃在自己身上。
* 全量并行（96 文件抢 CPU）时被拖过 20 s 超时线
  （`testTimeout: 20000`，见 `vite.config.ts:127`）。
* **判据：把我的改动 `git stash` 掉再跑全量 —— 同一条照样超时**
  （`20059ms`，994 passed / 1 failed）。→ 既存脆弱性，非本次引入。
* ⚠️ **对照必须跑两次**：第一次 stash 对照恰好**通过**了，只跑一次会得出
  「是我的改动害的」这个相反结论。flaky 的东西，单次对照没有证明力。
* 建议（**未做**）：给这条首用例放宽期望 / 单独 `testTimeout`，或别让它当「文件第一条」。

## 浏览器实测预览分页 —— 顺带挖出「分页从来没送出去」这个真根因

### 为什么非要做这一步
分页那个纯函数单测绿了，但**弹窗有没有真接上**没人验过。这正是我自己记过的
「UI 没浏览器实测」陷阱。实测第一轮就卡住：导航器**根本没出现** —— 因为
`pages` 是空的，而且不是我以为的那个原因。

### 真根因（比上一轮修的更深一层）
「预览区永远只有完整表」有**两层**原因：
1. 弹窗忽略 `RenderResponse.pages`（上一轮已修）；
2. **服务端压根没收到分页配置**。渲染请求体是 `{template, dump, sources}` —— **不带 options**；
   而服务端只认 `template.sheets[*].page`（`mod.rs:117`）。于是 `pages` 永远为空，
   **第 1 层修了也看不见效果**。

直接打服务端对照（同一模板两次）拿到硬证据：

| 请求 | 返回 keys | pages |
| --- | --- | --- |
| 原样（无 `page`） | `sheets, html` | 无 |
| 注入 `page:{rows_per_page:1}` | `sheets, html, pages, pages_html` | **6 页** |

TS 侧根因：`GroupTemplateOptions.page` / `CrossTemplateOptions.page` **都声明了却没人用**；
交叉表还把 `page` 传进构造器**又被丢掉**（`buildCrossTemplate` 返回值没 `page` 字段）。
**传一个会被丢掉的参数，比不传更容易让人以为已经接上** —— 这就是它能藏这么久的原因。
而服务端 `store::apply_options` 早实现了等价逻辑，但只在**打开已保存报表**时调用，
于是同一个开关「存下来执行」生效、「直接渲染」不生效。

### 修法
* 新增 `withPage(tpl, page)`（镜像 `apply_options` 的分页那半），在 `buildRequest` 里
  与 `withExportFormula` / `withExpandControl` 一起后处理 —— 放在 `rawTemplate` **之后**，
  这样存盘只存开关、由服务端再套，两条路才等价。
* 删掉那个会被丢掉的 `page` 实参 + 注释指路。
* `rows_per_page` 兜底为 1：服务端 `is_paginated` 要求 > 0，给 0 会**静默**退化成分页失效。
* 自由模板**不显示分页开关**：free 分支 `options` 只存导出公式/调试，分页既进不了存盘文件
  也进不了渲染请求，预览区装的又是模板本身。与「最少行数」那三个同一套理由 ——
  **不生效的开关就不显示**。

### 验证
* 浏览器抓到请求体 `sentPage = {rows_per_page:1, repeat_header_rows:1, repeat_footer_rows:0}`，
  响应 `pages` 长度 **5**，指示器 **`1 / 5`**。
* 点下一页 → `2 / 5`、画布指纹 `1966180200`；点上一页 → `1 / 5`、指纹 `-715134930`
  （**画布真换了内容**）；再点回来指纹**回到** `1966180200`（确定性）。
* 全程 `fetch` 计数**停在 2**（两次渲染）—— 翻页**没有再发请求**，「切页只重画」成立。
* 导出 xlsx 的请求体也带上了 `page`（此前不带，所以那句「按页出 sheet」当时是假的）。
* tsc 仍是 **3 条**（= 基线，改前改后各测一次，同码同位置只是行号平移）；
  `ts-test.sh` **125 → 132**（新增 7 条）；`mirror-check.py` 镜像一致。
* 探针：把 `withPage` 改成不写 `page` → **4 条红**；另外 3 条正确地保持绿
  （无 page 时原样返回 / rows 引用不变 / 构造器契约 —— 都不该被这个错影响）。

### 这次学到的
* **「客户端没送出配置」和「客户端没显示结果」是两个 bug**，只查渲染结果会漏掉前者。
  判据：把 `window.fetch` 打补丁**记下请求体**，别只看返回值。
* 自己文档里早就写着「请求级传 `page` 是无效的（实测 `pages` 为空）」—— **记了现象没追根因**，
  于是它躺了好几天。现象级笔记要配一句「那正确的那条路是谁在走」。
* 实测用的 dev server（vite 5188 / print-server 18888）收工后已停。
