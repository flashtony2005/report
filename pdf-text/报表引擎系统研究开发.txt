摘要
报表引擎是报表工具软件的核心组成部分，它控制报表系统的运行过程，为灵活多变
钓企业级报表展示提供强有力的软件支持。
在研究报表引擎工作原理、Eelipse 插件、RCP、XML、OSGI 等相关理论技术，剖析国
外先进报表引攀系统的基础上，作者提出了基于滑动窗口协议的报表引擎实现方案，设计
了一个具有一定特色的报表引擎系统体系结构，编码实现了一个可在 Windows 环境下运行
的报表引攀系统原型。该报表引擎具有报表运行引擎、策略引擎、展现引擎等基本软件模
块，可实现报表请求、格式定义、引擎定义、引擎运行、引擎监控、引擎输出等基本报表
工具功能。该系统原型为进一步开发实用报表系统奠定了良好基础。
本系统基于面向对象技术开发，采用 UML建模语言进行了报表引攀系统的分析与设
计，绘制（编写）了系统用例图及其用例描述、类图、包图、活动图等文档：应用伪代码
方法设计了主要软件模块的实现算法。最后在 Eelipse V3.2 环境下，用Java 语言实现了软
件系统。
本文将详细介绍作者的上述研究开发工作。
关键字：报表引擎；报表工具；报表系统：运行引擎：展现引擎；Eclipse：插件开发：
RCP; OSGI

1 概述
1.1 课题背景和意义
报表引擎，是报表软件的核心部分，是报表软件的控制中心。报表引攀软件系统包
括报表引擎运行器、策略引擎器、报表生成器等基本软件模块，可实现报表请求、格式定
义、引擎定义、引攀运行、引擎监控、引擎输出等基本报表工具功能。
报表引擎借鉴工作流引擎「2】 的流程运转原理运行。它首先接收来自报表设计器，基
于指定XML【31格式报表设计文件：然后对该文件进行格式检查、数据源查找、各种计
算处理、图形、图表处理：最后生成一个中间的二进制文档，发送给报表展示子系统，动
态生成 PDF、HTML、CSV【4］、SVG【S1等格式的报表。
报表引擎的功能与性能，在很大程度上决定了报表系统的功能与性能，决定了实用报
表应用系统的功能与性能。因此，进行本课题的研究开发，探索先进的报表马擎理论与技
术，开发功能强大报表引擎系统，以及具有一定特色的报表应用系统，对于促进我国政府、
企业、事业的报表信息处理水平，推动国民经济与社会的信息化快速发展，具有重要实
际意义，也有很好的学术意义。
1.2 国内外报表软件发展状况
报表处理一直是企业应用系统中最重要的一项工作，也是比较复杂的一个环节，因为
每一个企业都有自己的特色，要求有适合自己需求的报表系统。针对这个需求，国内外软
件企业纷纷推出各种各样报表引擎系统。下面分别介绍几种主要的报表引擎系统。
目前国外最有名气的报表工具软件主要有 Crystal Report “6,71 和 Active Report等。水
晶报表由美国 Crystal Decisions 公司开发。其主要特点是：可以从各种数据来源创建丰富、
交互内容，并将它集成到应用程序：可充分使用 Web 的优势，实现快速和交互的报表
系统；提供了完整的组件，可支持 Windows开发环境。目前，水晶报表已被公认为是高
效能报表系统的行业标准，微软在其.NET 开发平台捆绑的便是水晶报表。水晶报表的不
足之处在于难以开发一些格式复杂的报表，如带有斜线、交叉线等不规则报表；在报表
设计和使用方面不太符合中国企业习惯；软件费用比较昂贵。
Windward Reports 【1是一款轻量级的报表解决方案。其主要特点是：可以使用在各种
各样场合，可把该报表引擎安装在PC 机上作为一个单机版的软件来使用；或者安装在
服务器上，作为C/S或B/S结构的服务器来使用。任何语言都可以调用 Windward Reports
服务器端的服务。还可以把 Windward Reports 报表系统集成在微软的 Word 中，把 Word
作为报表设计工具，用 Word 进行报表设计。Windward Reports 输出格式包括 PDE, RTE，
HTML, WordML, SpreadsheetML, XLS or TXT等。但是，Windward Reports是一个轻量级
报表引擎，适用用于一些中小型应用：在与其它系统整合时比较费时、费力。
国内报表工具软件以用友华表公司 Cell【91 软件为代表，其内核采用了类似微软

EOS“TT】报表引擎是普元产品家族的一个重要组成部分，它有如下特点：支持三种数

SVG 等。
润乾报表「121是一款优秀的国产报表软件，在许多方面符合中国国情。其特点包括：
创新的报表模型、对跨平台大型应用的支持、HTML、EXCEL、PDF 报表展现方
式、填报功能、强大的 API 接口等。
润乾报表的主要缺点包括：瞄着高端路线，价格昂贵：外围功能做得较少、使用入门
比较困难。

1.3国内外报表引擎的发展状况
经过多年发展，报表引擎系统已经比较成熟，各种不同的报表引擎只是在公认技术
基础上突出自己在某方面的特色。已有的报表引擎系统体系结构分为三种：Java“13，报
表引擎、控件方式的报表引擎、独立服务方式报表引擎。
控件方式引擎：在浏览器端要安装一个 ActiveX 控件，在服务器端负责取数据，报表
的计算和生成都在控件中进行。采用这种方式的原因是它的报表功能往往都是用 Dephi
实现的，包括许多产品都是采用相同的第三方组件。
控件方式缺点在于：（1）部署：一个控件要完成别人在报表服务器上实现的大部分
功能。功能越强，控件体积越大，这对于部署是一个很大的负担。不仅如此，而且，当报
表系统升级时，用户都必须重新安装控件。（2）性能：在 PC 计算机与服务器端计算方面，
对于小报表差别不大，但对于大报表，差异非常大。并且，如果一个报表引擎系统由多个
用户使用，服务器的方式所可以采用的定时计算，缓存等等都无法发挥作用。
所以，控件方式一般只适用于简单小型报表，即报表样式简单；计算量，报表规模都
比较简单。
独立服务器引擎：这种方式安装一个（逻辑上）独立的报表服务器（包括报表引擎系
统）。它避免了空间方式的报表引擎系统部署繁琐，升级不便的缺点，能通过服务器有效
的管理报表，很好地处理性能问题。但它部署起来也是比较麻烦，实际上这类报表引擎系
统很难做到跨平台。尤其是如果涉及集群，连接池等问题，它就无法提供良好可扩展性。
Java 报表引擎：可以轻松的实现报表钓跨平台部署。有与独立服务器相同的优点与
缺点。对于 Java应用，则可以类包钓方式将报表软件最入到J2EE应用架构中，与应用系
统形成无缝衔接。这时，它的优势就更加明显：Java 应用服务器的所有提高性能的手段，
都可以在报表系统上充分发挥作用，如计算能力更强的服务器、负载均衡、连接池等；报
表系统可以与应用程序更紧密地衔接，被应用程序更灵活地使用。
报表引擎虽然已成为一个成熟的技术，但在某些具体方面还是有很大的研究空间的，
目前报表引擎研究主要专注与跨平台且具有独立的服务器功能方面，除此之外，根据不
同地区的报表具有很好解析功能也是报表引擎研究热点。

2.1.2平台运行时
平台运行时（Runtime）相当于一个微内核，是插件的核心引擎。它位于平台核心中
最低级别的部分，由 org.eclipse.osgi 和 org.eclipse.core 这两个插件组成，其他所有的插件
都依赖于这两个插件。
Runtime 功能
◆定义插件的结构以及它们包含实现详细信息（bundle 和类载入器）。
◆ 查找和执行主要的 Eclipse应用程序以及维护插件的注册表、扩展和扩展点。
◆ 提供实用程序（如记录、调试跟踪选项、适配.、首选项库和并发性基础结构）。
Runtime 的工作原理
Runtime 管理着一个插件注册表（所有插件的标识），当 Eclipse 启动时，Runtime内
核先定位JRE的位置，然后启动 startup.jar扫描 plugins 和 features目录下的插件配置文件，
对插件进行初始化，把插件注册到 OSGI（ Open Service Gateway Initiative，开放服务网关
协议）中，并保存配置文件中的信息。然后查找清单文件中声明的 extension point 和
extension，将二者匹配，保存插件的依赖关系。最后启动应用。
只有当需要使用插件时，Runtime 才将其调入内存；不需要时选择适当时机把插件
清除出内存。
2.1.3 OSGI
Eclipse 体系架构是参照 OSGi 181 （Open Service Gateway Initiative，开放服务网关倡
议）实现。核心插件 org.eclipse.osgi 就是 OSGi的实现。
OSGi是一个为家用硬件设备的远程互访建立的一个开放的规范。它包括构建开放的
可交付网络服务的各方面。
OSGi中的应用称为 bundle，每个 bundle 可提供一定数量服务（Services）。每一个
安装在OSGi服务平台 bundle 都有一个与之关联的 bundle 对象（object），它负责管理
bundle 的生命周期。bundle有诸如安装、停止、活动等多种状态。
OSGI主要规范如下：
框架规范（Framework）：是 OSGi规范的核心，提供了一个通用、安全可管理Java
框架以及管理bundle 安装和更新的功能。bundle 安装后会注册一定数量的服务，可被同一
Framework 下的其他 bundle 使用。不同 bundle 提供 Services 可构成一个大规模的
Services，不同 bundle 和 Services 形成依赖。这种依赖关系由 Framework负责管理。
Framework 为 bundle 提供了代码动态加载的功能，OSGi兼容设备可以任意加载和卸载
OSGi bundle。使得开发者开发、部署一个大规模 Services 变很容易。Framework 还为
Java bundle 开发者提供了简明一致编程模型，允许开发者将自己接口规范绑定到
OSGI环境中的 Services。

2.2.2 DTD与 XML Schema
报表的格式和数据都存储在 XML格式的文档中，为了能够有效的定义报表格式和
组织报表的数据，需要定义词汇表来验证和规范报表和数据文档。目前 W3C （World Wide
Web Consortium,W3C 委员会）推荐两种方式定义词汇表：DTD（Document Type Definition，
文档类型定义）、XML Schema。
文档类型定义DTD 是一套关于标记符的语法规则，它提供了一个 XML文档中元素、
标记、属性、实体的清单以及它们之间关系，一个有效的 XML 文档必须遵循 DTD 已
声明的种种规定，简言之，DTD 就是一个标记语言的语法和词汇表。
XML Schema 是在DTD 的基础上发展起来的，功能比DTD 更强大：可以定义每个元
素的实际数据类型：从其它模式继承语法；创建简单和复杂的数据类型：定义元素可能出
现次数的最多值和最小值。DTD 和 XML Schema 各有优缺点，主要表现在：
◆ DTD是 W3C 1998年2月推荐规范，使用 EBNF （Extended Backus-NaurForm）
语法描述元数据，对于那些不熟悉 EBNF语法使用者具有一定的难度。
◆ XML Schema 221是 W3C 2001年5月确定的推荐标准，XML Schema 使用 XMIL
语法，使用者不必花费太多的时间就能掌握。
• DTD支持数据类型少于 XML Schema，在描述数据类型方面有一定的缺陷。
◆ DTD 的定义非常简洁，而 XML Schema定义比较复杂，同一个词汇表DTD的
定义大概只有 XML Schema 一半。
◆ 采用 DTD 规范偏重于开发语言，适合专业编程人员；而采用 XML Schema 规
范偏重于 XML提供技术，适合设计人员。

2.2.4文档对象模型
DOM （Document Object Model） 即文档对象模型，是解析和处理XML文档的常用
API之一。DOM 以分层次对象模型来访问存储在XML中的信息，在处理 XML文档时，
生成一棵节点树，并把文档中文本信息转变成一组树的节点。DOM 使用树状模型来访
问 XML文档中的信息，由于XML文档是分层次的，所以 DOM 这种模式处理 XML文档
十分清晰明确。
DOM 是一个独立于平台和语系的接口，是相关于文档的一系列对象列表，通过操作
这些对象，可对 XML文档进行读取、遍历、修改、添加和删除。在DOM 中最基本的对
象是 Node，从 Node中又派生出了几种具体的节点类型。对应于XML中各种相应的节点。
在使用 DOM 加载 XMIL 文档后，在内存中形成一个节点树，由 XML 各种节点形成各种
对象模型组成。这些对象包括相应的属性、方法，以对数据进行操作。
DOM中有几个基本对象：
【1】
document，这个对象参照到整个文档，是对文档操作的入口。
【2】
element 和 attribute，这是文档中的某一部分的映射，节点层次，反映了文
，档的层次。
【3】
text，这是 element或属性节点的内容，不再包括子元素。
DOM 中的所有节点，都是从NODE节点继承而来的，它包括一些基本属性与方法，
通过这些属性和方法，可以对文档遍历，还可取得节点名称、取值和类型。它将 XMI
中的所有项目看成节点：元素、属性、文本、注释、处理指令等。DOM韵接口与具体
平台和语言没有关系，因此在J2EE平台和.NET 平台下有不同的实现，常见的有DOM和
基于 Java 语言实现的 JDOM，dom4j等。J2EE 框架的类库对XML提供了大量的支持，
并且符合 W3C标准，性能高，可扩展性好，为 XML的文档处理提供了有力的支持。

3 报表引擎系统的需求分析
3.1 功能分析
根据上文对国内外同类产品的分析以及国内企业用户的需求，我们获得了报表引擎应
该具有的功能如下：
1） 能处理各种各样的报表，特别是企业遇到的一些特殊格式的报表。
2）跨平台，能在 Windows、Linux平台下运行。
3）可支持多数据源。从以不同的形式存储的数据源中提取数据，并生成报表。
4） 具有统计，分组，过滤功能。
能产生图表，形象地展现报表数据的分布情况。
6） 支持各种形式的报表输出，如 Excel、PDF、HTML 等形式，以应对各种各样的企
业需求。
7）
有比较完备的错误处理机制，以及运行监控机制。
8）
支持 C/S 及 B/S 模式运行。
9） 报表引擎可作为一个插件晚入到一些可视化设计软件（如 Word、Eclipse）中。
10） 报表符合中国企业的习惯，支持斜线。
11） 支持报表权限管理，控制用户对报表系统的访问权限。
3.2 模块分析
报表引擎从整体上划分为：报表请求器鄙分，格式定义部分，引擎定义部分，运行引
繁部分，策略引擎部分，引擎监控部分，展现引擎部分。每一部分都是独立运行的一个模
块。它们之间经过相互协调工作，共同完成整个报表从定义、请求、执行、监控、分派、
显示功能。
整个报表引擎的核心的部分是报表引擎运行器、策略引擎器以及报表生成器。其它几
是报表引擎辅助部分，协调报表引擎的运作。
报表请求器：主要是实现对报表请求参数的封装，实现统一的入口。并负责对请求及
响应的集中控制、分配。该模块的用例图「251如图3-1。

3.3 流程分析
在报表引擎定义器中，定义报表引擎的主题信息、计算策略，并根据定义的内容，生
成报表引擎的定义文件（XML 文件）。报表引攀运行器运行时，自动根据系统的配置信
息，导入定义好的格式文件，并解释成报表引擎能操作的对象。
用户请求报表引擎执行报表计算时，传入起动参数及报表的 ID，报表引擎在配置文
件中查找要计算的报表。找到报表定义文件后，实例化报表約定义对象，并根据算法钓执
行次序，起动整个报表的执行过程。在报表的每一个算法中，根据定义的形式参数从系统
环境中读取实际参数值。如果算法是一个表达式，系统启动策略引擎器进行计算，再返回
运算的结果；如果算法是调用外部的应用程序或过程，系统会自动根据定义的内容及参数，
调用相应的应用程序或过程进行运算，并保存运行的结果。
在报表引擎运行过程中，报表引擎监控暴可以跟踪报表的执行过程，并记录它的执行
过程；也可以对运行钓报表执行暂停、中止、恢复、保存、载入等操作。用户可以根据报
表的运行情况，分析报表的各种性能及调整报表的执行过程，优化报表引擎的性能。
当报表引擎运行结束后，返回运算结果，报表生成器根据用户在报表格式定义器中定
义的报表格式，生成相应的报表，再展示给用户浏览。

5.2.3 滑动窗口协议思想在报表引擎系统中的实现
滑动窗口协议是一种数据传输协议，根据具体应用又可把它细分成多种协议：比特滑
动窗口协议、后退n协议、选择重传协议。本系统应用的是选择重传协议，下面详细介绍
这个协议。
窗口机制：滑动窗口协议的基本原理是在任意时刻，发送方都维持一个连续的允许发
送帧的序号，称为发送窗口：同时收方也维持了一个连续的允许接收帧的序号，称为接收
窗口。发送窗口和接收窗口的上下界不一定相同，甚至大小可以不同。不同的滑动窗口协
议，其窗口大小一半不同，发送窗口内的序号代表了那些已经被发送，但是还没有被确认
的帧。
选择重传协议：发送方发完一个数据后不是停下来等待应答帧，而是连续发送若于个
数据帧，即使在连续发送过程中收到了接收方发过来的应答帧，也可以继续发送。接收方
发现收到的帧出错时，其后继发过来的帧不能立即提交给接收方的高层，但接收方仍然可
以接收下来，存放在一个缓冲区中，同时要求发送方重新传送出错的那一帧。一旦收到重
新传来的帧后，就与原存于缓冲区的其余的帧一起按正确的顺序递交高层。
通过本文前面对报表引擎系统的介绍，我们知道报表引擎系统分为七个模块，每个模
块在指定时间处理报表的相应部分，如果没有合适调度算法，就会使得系统中后面模块
的等待时间过长，从而使报表引擎系统的效率大大降低。如果在实现时加入一定的调度算
法，协调报表引擎各组成模块的工作，就会使得各个模块之间等待时间大大减少，从而
提高报表引擎钓运行速度。
为了提高系统的速度，本系统采用了前面提到的选择重传协议，用来控制报表引擎各
个模块的工作。本系统应用选择重传协议的基本思想是：首先，发送模块从上游模块接收
已经被上游模块处理的报表模块，并在本引擎模块对报表模块进行相应的处理，为每个报
表模块设定定时器；然后把已设定好定时器的模块发送到下游模块，并把己发送模块放入
到缓冲区缓存起来，发送模块随即进入监听状态；接收模块收到报表模块立即向发送方发
出确认信息，如果没有收到发送出错信息；接受模块收到确认信息，立即清除缓冲区对应
的模块。如果定时器超时或收到出错信息，立即从缓冲区中取出相应模块重新发送。

Eclipse 集成开发环境和 Java 语言，设计实现了一个具有一定特色报表引擎。
报表引攀是一个大型复杂软件系统，为了方便开发，作者把整个报表引擎按功能划分
为报表请求、格式定义、引擎定义、引攀运行、策略引擎、引攀监控、引擎展现七个子系
统。然后应用 Eclipse 的插件开发技术，把每一个子系统作为一个插件工程实现。这样做
能够保证子系统之间的松散耦合，使得系统某一部分变化部分不会影响到系统的其它部
分，使得系统维护以及软件模块复用更加容易，团队合作开发也更加方便。
此外，为了把报表设计信息长期保存下去，以便后来复用，本系统采用 XML技术保
存报表的设计信息。利用这些设计信息，有用户就可以方便地使用或修改以前所设计报
表格式，而不用费时、费力的重新设计了。
目前，该系统已经能够进行一些基本的报表解析工作，但是对于一些复杂的报表解
析，特别是流行于中国式报表中的交叉格式报表的解析还是显得捉襟见肘。因此下一步的
工作是继续努力，攻克复杂报表解析这一难题。
